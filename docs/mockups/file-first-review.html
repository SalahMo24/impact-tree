What each piece is, and the VS Code API behind it

  1. One review view. The TreeView from today. The Findings / Other / Deleted / No test / Files sections are gone; every changed file is one top-level row. The filters and "next" are view/title menu commands with toggled icons.
  2. Summary line. TreeView.message (the text above the tree), plus TreeView.badge on the activity icon for "left to review". It replaces the summary row and the Legend section.
  3. File rows, worst first. A file ranks by its worst change; files with nothing risky drop to the bottom. Its checkbox is derived: ticked when every counting row is ticked, which is exactly when the file is marked viewed on GitHub (proposal a). The dashed purple pieces arrive with the review loop.
  4. Change rows. One per changed or deleted symbol, plus "Outside functions". The lead glyph is the review verdict, and the risk kind is a chip. Body-only edits don't lead with ⛔: their callers are expected to be unchanged (see Decisions, Q1).
  5. Impact rows. A change's callers (✓ updated at the call · △ changed elsewhere · ○ untouched) and its tests. Callers never have a checkbox: they don't count towards "viewed".
  6. Detail panel. A WebviewView under the tree that explains one change in sentences: the verdict, the signature before and after, callers (each opens the peek) and tests, with Mark reviewed / Next. It follows the tree selection and the cursor in the review diff (window.onDidChangeTextEditorSelection on the diff's right side), and the tree reveals the same row (TreeView.reveal). Click any line in the diff, or move with the arrow keys, to try it.
  7. Status bar. A StatusBarItem with what's left and how many rows need attention; clicking it runs "next unreviewed" (⌥N, a contributed keybinding).
  8. Diff CodeLens, attention only. A CodeLensProvider on the review diff's right side, only on changes that need attention (⛔ or ?): verdict · Show callers (opens the peek) · Mark reviewed. On PR #15 that is 3 lenses, not 52; body-only edits get no lens, and the panel carries their details.
  9. Callers peek. editor.action.peekLocations with the call sites: the same peek widget as "Find references", so it needs no custom UI. Opened from a lens, a caller in the panel, a caller row in the tree, or the "Show callers" command (⇧⌥C) on any changed function under the cursor.
Impact Tree: Changes by blast radius

The same PR in today's tree

The tree is laid out by analysis category (Findings, Other changes, Deleted, No test reaches, Files without a call graph, Legend), not by the path a reviewer takes. To review src/github.js you visit the Findings section, the Other changes section and its own file group, and its outside-functions row sits apart again.

Every body-only change whose callers did not change leads with ⛔ "call site(s) not updated". For a body-only edit that is the normal case, so the one real signature risk (allHunks: a new parameter that the caller in diff.js:133 doesn't pass) looks the same as thirty routine edits.

The proposed tree keeps every one of these facts and still shows a count for each. It changes only the order they are grouped in and which ones lead.
